# Decisions

A running log of product and technical decisions, with the reasoning, so future-us (and agents) don't re-litigate them. Newest at the bottom. If a decision changes, add a new entry that supersedes the old one rather than deleting it.

---

## D1 — Access by per-person invite codes, not a shared password

*Decided: 2026-11-01*

Each member gets their own invite code (e.g. `tiger-ferry-42`), generated by the admin.

- The code is **both the key and the identity**: entering it links you to an anonymous member ID. No name, no email.
- **Revocable one at a time.** A leaked code can be cancelled without affecting anyone else.
- **Guessing protection:** codes are long and random, plus a soft server-side slowdown after a few failed attempts (rather than a hard "3 strikes" ban by IP, which is bypassable, can lock out innocent people on shared Wi-Fi, and means storing IP addresses).
- **"Remember this device"** after the first entry, so the code is typed rarely. Entering the code on a new device restores your identity — this is also the recovery method.
- Codes are stored hashed, never in plain text, and never in the repository.

**Why:** a shared password gives everyone the same identity (so no "my submissions", no one-rating-per-person) and a single leak means rotating it for everyone.

## D2 — One shared pool of questions is the core model

*Decided: 2026-11-01*

There are no personal question banks or private playlists by default. Everyone who's in contributes to and draws from one pool.

- Ratings become meaningful as a group signal.
- Playlists (later) are shared curated sets, visible to all members.
- Private drafts are a maybe-later, only if someone asks for them.

## D3 — Only the admin can invite (for now)

*Decided: 2026-11-01*

The admin creates and revokes codes, with a private note per code (e.g. who it's for). Member-to-member invites may come later, with a cap.

## D4 — New questions wait in an approval queue

*Decided: 2026-11-01*

- Submitted questions are **pending** until the admin approves, edits or rejects them.
- Submitters can suggest tags; the admin finalizes them at approval (keeps tags consistent).
- Submitters privately see the status of their own submissions (pending / approved). Rejected ones quietly disappear.
- The admin sees a "N pending" badge in the app. Email notifications: not in v1.
- Nothing is hard-deleted; questions are hidden, so everything can be undone.

## D5 — No nicknames or credits

*Decided: 2026-11-01*

Contributions are not attributed publicly.

## D6 — Designed so real accounts can be added later

*Decided: 2026-11-01*

Every member has an internal anonymous ID from day one, and all data hangs off it. If real accounts are ever wanted, a member attaches a login method (email / passkey) to their existing ID and keeps their history. We use an existing auth/database provider that supports this rather than building login ourselves.

Adding real accounts would mean holding personal data (privacy policy, GDPR obligations), so it's deliberately deferred.

## D7 — Sessions: one phone, ~5 questions, optional 1–10 rating

*Decided: 2026-11-01*

- A session is ~5 questions shown one at a time on a single device. Multi-device sync is out of scope for v1.
- Each question can be **skipped**, **rated 1–10** (optional) or passed. You can leave anytime.
- Speed matters: open app → pick theme → first question in about two taps.
- Should work offline and be installable to the home screen.

## D8 — Question taxonomy

*Decided: 2026-11-01*

Each question has:

| Field | Values | Notes |
|---|---|---|
| `topics` | free-ish list (e.g. childhood, work, love, values) | what it's about |
| `situations` | fixed list — see below | the setting it suits |
| `intensity` | `light` · `medium` · `deep` | so a session can avoid going too heavy too soon |

Situations (fixed): `just-met`, `date`, `friends`, `old-friends`, `group`, `family`, `work`.

## D11 — Public repo, secrets never in code

*Decided: 2026-11-01*

- The repository is public from day one.
- All secrets (admin code, invite-code salt, database credentials) live in the hosting provider's environment variables.
- `.env` files are git-ignored; GitHub secret scanning is on.
- If a secret is ever committed, treat it as leaked and rotate it — deleting the file does not remove it from git history.
- Licenses: code MIT, starter content CC BY 4.0.

*Decided: 2026-11-01*

Static front end + Netlify Functions for anything server-side. Database / auth provider to be chosen at Phase 2.

## D13 — How a session picks and orders questions (Phase 1)

*Decided: 2026-11-01*

- The start screen asks **who you're with** (a situation) and **how deep** (Light = light only, Mixed = all, Deep = medium + deep). Depth is remembered on the device. Tapping a situation starts the session straight away.
- Questions this device has seen least recently are picked first, so rounds don't repeat until the pool runs out.
- The picked questions are shown **light → medium → deep**, so the conversation warms up.
- **Swap** replaces the current question with another of the same intensity if possible, and doesn't use up one of the five. If nothing is left to swap in, the question is dropped.
- A rating is saved when you move on (Next, Swap or Leave). Tapping the selected number again clears it.

## D14 — Stack

*Decided: 2026-11-01*

React + TypeScript, built with Vite, made installable/offline with vite-plugin-pwa. No external fonts or scripts, so it works fully offline. Netlify builds with Node 20.

## D15 — How changes go live: branch → Pull Request → preview → merge

*Decided: 2026-11-01*

- Netlify publishes the **`main`** branch. ~~`main` always equals what's live.~~ Publishing is now manual — see D18.
- **Nobody commits to `main` directly.** Each piece of work gets its own branch (e.g. `feature/invite-codes`, `docs/…`, `fix/…`).
- When it's ready, a **Pull Request** is opened into `main`. Netlify builds a **Deploy Preview** for it — a temporary address running exactly that version — without touching the live site.
- The admin checks the preview (ideally on a phone). **Merging the Pull Request is the "publish" button.**
- If something goes wrong after a merge, roll back to a previous version from the Netlify dashboard (Deploys → pick a deploy → Publish deploy).

**Why not a separate `deploy` branch?** Two long-lived branches drift apart, add an extra sync step every time, and still don't let you see a change working before it's live. Deploy Previews give the same separation more simply.

**Later (Phase 2):** previews must not use the live database. Set up a separate database (and environment variables scoped to "Deploy Previews") before any database feature reaches a Pull Request.

## D16 — Database: Netlify Database (Postgres), plain SQL

*Decided: 2026-11-01*

- **Netlify Database** (managed Postgres via `@netlify/database`). It runs on the Free plan's monthly credits.
- Every Deploy Preview automatically gets its **own copy of the database** (a branch), so previews never touch live data (meets D15). Previews are team-protected, which matters because a branch starts as a copy of production data.
- Schema changes are **migration files** in `netlify/database/migrations/`, applied automatically on deploy. A migration that has been deployed is never edited — a new one corrects it.
- Queries are plain SQL (no ORM): the schema is small and stays readable.
- The starter questions were imported into the database by a migration. `content/questions.json` remains the public source for them, and the app falls back to it on a device that has never been online.
- Login is our own invite-code check (D1) on top of this database, not a separate auth provider. Adding real accounts later (D6) would mean adding one.

**Why not Supabase?** Its free tier pauses after a week of no use, and keeping previews off the live data would take manual setup.

## D17 — How the invite-code gate works

*Decided: 2026-11-01*

- **The whole app is behind the code screen.** Without a code you see only that screen. (The 30 starter questions are public in the repository anyway; member questions are not.)
- **Codes** look like `tiger-ferry-lamp-42`. Capitals, spaces and underscores don't matter. They are stored only as a keyed hash (HMAC-SHA256 with a secret key, `CODE_PEPPER`).
- **The admin's code** is the `ADMIN_CODE` environment variable, not a database row. Changing it signs the admin out everywhere.
- **"Remember this device"** is automatic: a successful code sets a signed, HttpOnly cookie for a year. Every request re-checks that the member's code hasn't been revoked, so revoking a code locks that person out at once. "Forget this device" on the home screen signs the device out; the code keeps working.
- **Offline:** a device that has entered a code before opens straight away and runs on the questions it last downloaded. The server check happens in the background.
- **Soft slowdown:** each failed attempt in the last 15 minutes, from anyone, adds 0.4 s to the next check (up to 5 s). Failures are logged with a time only — no IP or device details.
- **Secrets:** `ADMIN_CODE`, `CODE_PEPPER` and `SESSION_SECRET` live in Netlify's environment variables, with different values for Production and Deploy Previews. See `.env.example`.

## D18 — Publishing is manual (amends D15)

*Decided: 2026-11-01*

- Auto-publishing is **off** in Netlify. Merging a Pull Request into `main` builds it, but **doesn't make it live**.
- The admin publishes by hand (Netlify → Deploys → pick the newest `main` deploy → **Publish deploy**), only when the work needs it or a big milestone ships (e.g. the end of Phase 2).
- **Database migrations run when a deploy is published**, not when it's merged. Anything production needs first (e.g. environment variables) must be in place before publishing.
- Each Pull Request says whether it needs publishing, and what must be set up first.

**Why:** saves Free-plan credits on small changes, and keeps half-finished phases off the live site.

## D19 — Shared ratings and suggestions (Phase 2)

*Decided: 2026-11-01*

- **Ratings** are saved on the phone first, then sent when there's a connection (right away, on opening the app, or when the phone comes back online). One rating per member per question: the **most recently given** one wins, even if an older one arrives later.
- Ratings given on a phone before Phase 2 are uploaded once, the first time that phone enters a code. "Forget this device" stops anything left over from going to the next person's code.
- **Suggesting a question:** the text (10–300 characters), at least one situation, a depth, and optional topics. Topics are only a hint; the admin sets the final ones at approval (D4). At most 20 suggestions per member waiting for review at once.
- **Your suggestions** shows each one as "Waiting for review" or "In the pool". Rejected ones simply disappear from the list (D4).

## D20 — The admin screen

*Decided: 2026-11-01*

- Only the admin sees the **Admin** button on the home screen, with a "N pending" badge when suggestions are waiting.
- **Review:** suggestions are listed oldest first. The admin can fix the text, situations, depth and topics, then **Approve** (it joins everyone's pool) or **Hide** (it disappears from the submitter's list; nothing is deleted).
- **Invite codes:** each new code gets its own anonymous member and a private note (e.g. who it's for). The code is shown **once**, with a Copy button, because only its hash is stored. A lost code is revoked and replaced, not recovered.
- **Revoking** asks for confirmation, then signs that person out on their next connection.
